# データモデリング比較：Claude単独版／Qiita記事参考版／ルールベース版

## 1. 比較の目的

本書は、同一の要件（[requirements.md](../requirements/requirements.md)）に対して行った3通りの
モデリング結果を観点別に比較し、それぞれの長所・短所を整理した考察ドキュメントである。

- **claude-only版**: Claude単独の判断のみでモデリングした結果。
  [claude-only/data-model.md](claude-only/data-model.md)
- **qiita-reference版**: 依頼者が過去に執筆したQiita記事3本（テーブル分類と関連の作り方／ER図の
  レイアウト原則／受注・出荷の多重関連と在庫金額計算の実務的課題）を参考に再モデリングした結果。
  [qiita-reference/data-model.md](qiita-reference/data-model.md)
- **rules-based版**: qiita-reference版の検討過程で得られた知見を一般化した
  [CLAUDE.md](CLAUDE.md)（設計ルール）と、[requirements.md](../requirements/requirements.md)
  （要件定義書）の2文書だけを根拠に、他の設計書を一切参照せず独立に行ったモデリング結果。
  [rules-based/data-model.md](rules-based/data-model.md)

claude-only→qiita-reference は「参考資料の有無による差」を、qiita-reference→rules-based は
「個別の参考記事ではなく、そこから抽出した一般ルールだけでどこまで同じ結論に到達できるか」を
確認する比較軸になっている。

## 2. 観点別比較（データモデル）

### 2.1 テーブル分類の考え方

| | claude-only版 | qiita-reference版 | rules-based版 |
|---|---|---|---|
| 分類の明示 | なし（マスタ／トランザクションという通俗的区別のみ暗黙的に使用） | 「マスターテーブル／ステートテーブル／トランザクションテーブル」を明示的に分類 | 同左。CLAUDE.mdの「テーブル分類を明示する」ルールをそのまま適用し、分類根拠（会員は利用者自身が繰り返し更新するためステート、等）も明記 |

claude-only版はこの分類軸自体を持たないのに対し、qiita-reference版・rules-based版はいずれも
分類を明示しており、この観点では両者は一致している。CLAUDE.mdに明文化されたルールが、qiita記事を
直接読んでいないrules-based版でも同じ判断を導けていることが分かる。

### 2.2 関連構築の優先順位

claude-only版は一般的な業務システムの設計パターン（マスタ－トランザクション－明細）に沿って関連を
構築しており、特定の優先順位の原則は明文化していない。qiita-reference版・rules-based版はいずれも
「トランザクション同士を業務プロセスの発生順に直接関連づけることを優先する」という原則を明示的に
採用しており、結果として仕入れ系列・販売系列ともトランザクションの連鎖として追跡可能な構造になって
いる。この点はclaude-only版も結果的に近い構造（仕入れ→入庫、販売→出庫）を採用していたため、
3版の差は小さい。

### 2.3 販売系列の構造（最大の差分）

| | claude-only版 | qiita-reference版 | rules-based版 |
|---|---|---|---|
| 構造 | 販売（受注）1 : N 出庫 | 受注 1 : N 受注明細、受注明細：出荷 が 出庫（中間テーブル）を介して N : N | 同左。受注・出荷・出庫の3層構造 |
| 分割出荷への対応 | 不可 | 可能（受注明細ごとに複数の出庫レコードを作成できる） | 可能（同左） |
| まとめ出荷への対応 | 不可 | 可能（1つのshipmentに複数の受注由来のstock_outを集約） | 可能（同左） |
| 出荷が会員を直接参照する理由の説明 | （構造自体がないため該当なし） | まとめ出荷時に受注を介さず配送先を特定するため | 同趣旨をより明示的に記述（「出荷の配送先は特定の受注1件に従属しないため」） |

qiita-reference版とrules-based版は、テーブル構成・関連の向き・多重度のいずれも実質的に同一である。
rules-based版はqiita記事そのものを読んでいないにもかかわらず、CLAUDE.mdの「多対多は中間テーブルで
解消する」ルールだけから、qiita-reference版と同じ中間テーブル「出庫」の構造に到達している。これは
記事3（受注と出荷は実際には多対多になる）の知見が、ルールとして十分に一般化・言語化できていた
ことを示している。

### 2.4 仕入れ系列の構造

3版とも「仕入れ 1 : N 入庫」という同一の2層構造で一致している。qiita-reference版・rules-based版は
いずれも「対称性のために仕入れ側も三層化する選択肢はあるが、仕様に『入荷』に相当する語が存在しない
ため見送る」という同じ判断過程を明記しており、CLAUDE.mdの「オーバーエンジニアリングを避ける」
ルールが意図通りに機能している。

### 2.5 ステータス管理

| | claude-only版 | qiita-reference版 | rules-based版 |
|---|---|---|---|
| 進行状況の保持方法 | `status` カラムを保持し、アプリケーション側で更新 | `status` カラムを廃止し `is_cancelled` のみ保持。進行状況は入出庫実績の集計から動的に導出 | 同左。カラム名・考え方とも一致（`is_cancelled` のみ保持し、進行状況は実績集計から導出） |

qiita-reference版とrules-based版はここでも一致している。claude-only版は実装がシンプルだが、
`status` と実際の入出庫実績が食い違う（更新漏れ等）リスクを内在する。

### 2.6 属性の網羅度（qiita-reference版とrules-based版の差分）

構造面でほぼ完全に一致する一方、属性レベルでは差分がある。

| | qiita-reference版 | rules-based版 |
|---|---|---|
| 監査列（created_at/updated_at） | 全テーブルに付与 | 付与なし |
| 業務番号（purchase_order_number等） | 付与 | 付与なし |
| 商品区分（product_type） | 付与 | 付与なし |
| 会員の配送先住所 | 住所カラムを保持 | 同様に保持（カラム名はshipping_address） |
| 物理名の命名規則 | 日付系は `order_date` 方式 | 日付系は `ordered_on` 方式（表現は異なるが意味は同じ） |

これはCLAUDE.mdが「テーブル分類」「関連の作り方」「ステータス導出」「ER図レイアウト」といった
**構造上の判断基準**を中心にルール化しており、「どの属性を一律で持たせるべきか」「物理名の命名規則」
といった**属性・命名レベルの一般原則**までは明文化していないために生じた差である。構造的な設計判断は
ルール化によって再現できたが、属性の網羅性や命名の細部はルール文書の記述密度に依存することが
確認できた。

### 2.7 在庫金額計算への言及

claude-only版は数量ベースの在庫算出のみに触れている。qiita-reference版は記事3の知見（先入先出法・
総平均法等による金額差異）を将来の留意点として明記している。rules-based版はCLAUDE.mdに在庫金額
計算のルールが含まれていないため、この論点には触れていない（要件定義書のスコープ外一覧には
記載があるため、対象外という扱い自体は3版で一致している）。これも、参考記事の持つ「将来の拡張時の
勘所」のような暗黙知は、構造ルールに要約した時点で失われやすいことを示す一例である。

## 3. rules-based版固有の考察：ルール化の再現性

rules-based版は、qiita-reference版のモデリング過程で得た知見を要約した CLAUDE.md と、要件定義書の
2文書のみを根拠に、他の設計書を参照せず独立に作成されたものである。両者を比較することで、
「個別の参考資料」を「一般化したルール」に変換した際に、何が引き継がれ、何が失われるかを確認できる。

| 再現できた点 | 再現できなかった点 |
|---|---|
| テーブル分類（マスター／ステート／トランザクション） | 監査列（created_at/updated_at）などの定型的な属性 |
| 受注・出荷・出庫の3層構造（多対多の中間テーブル解消） | 業務番号・商品区分など要件に明記のない補助的な属性 |
| 仕入れ・入庫の2層構造（対称化を見送る判断） | 物理名の命名規則の細部（語尾の表記ゆれ） |
| ステータスの動的導出と`is_cancelled`の個別保持 | 在庫金額計算のような参考記事固有の周辺知識 |
| 在庫算出式（棚卸し基準＋入出庫調整） | ― |
| ER図のレイアウト（A4横・直角線・鳥の足記法・色分け・マスタ複製配置） | ― |

この結果から、CLAUDE.mdに書き出したルールは、**構造的な設計判断（テーブル分類、関連の作り方、
多対多の解消、ステータス管理、在庫算出ロジック、ER図のレイアウト）を再現するには十分な情報量を
持っていた**と言える。一方で、個々のテーブルにどこまで属性を持たせるか、物理名をどう命名するかと
いった実装の細部は、ルール文書に明記しない限り作成者（モデラー）の裁量に委ねられ、揺らぎが生じる
ことが分かった。ルールをさらに精緻化する場合は、「監査列は全トランザクション／マスターに付与する」
といった属性レベルの原則を追記することで、再現性をさらに高められる。

## 4. 総括（データモデル）

| 観点 | 優れている版 | 理由 |
|---|---|---|
| 仕様文言との整合性 | qiita-reference版／rules-based版 | 仕様に明示される「出荷」と「出庫」を別概念として扱える |
| 実務的な表現力（分割・まとめ出荷） | qiita-reference版／rules-based版 | 出庫を中間テーブルとすることで多対多を自然に表現 |
| シンプルさ・学習コストの低さ | claude-only版 | テーブル数・関連数が少なく、素直な構造 |
| データ整合性の強さ | qiita-reference版／rules-based版 | ステータスの二重管理が発生しない |
| 実装・クエリの容易さ | claude-only版 | 進行状況をカラム参照のみで取得できる |
| 属性の網羅性 | qiita-reference版 | 監査列・業務番号等、実装時に必要になりやすい属性を含む |
| 再現性の検証可能性 | rules-based版 | 参考資料なしでも同じ構造に到達できることを示し、qiita-reference版の判断が属人的な勘ではなくルール化可能な原則だったことを裏付けた |

claude-only版は「標準的なECシステムのデータモデル」として素直で分かりやすいが、仕様文中に明示される
「出荷」という概念を独立したトランザクションとして扱えておらず、実務で頻発する分割出荷・まとめ出荷に
対応できない。qiita-reference版とrules-based版は構造的にはほぼ同一の結論に達しており、違いは属性の
網羅度と命名の細部にとどまる。これは、Qiita記事という個別の経験知を一般化したルール（CLAUDE.md）が、
記事を読まない第三者の視点からも同じ構造的結論を導けることを示しており、ルール化の妥当性を裏付ける
結果である。

## 5. ER図の比較

実際に作成したER図についても、データモデルと同じ3版で比較する。

### 5.1 claude-only版 vs qiita-reference版（モデル構造の違いが図に与える影響）

比較対象は、どちらもMermaidの自動レイアウトエンジンに任せて1枚にまとめた全体図である。

- claude-only版: [claude-only/er-diagram.png](claude-only/er-diagram.png)
- qiita-reference版: [qiita-reference/er-diagram.png](qiita-reference/er-diagram.png)

| 観点 | claude-only版 | qiita-reference版 |
|---|---|---|
| 販売系列のエンティティ数 | 受注・受注明細・出庫・出庫明細の4つ | 受注・受注明細・出荷・出庫の4つ（出荷が新規） |
| 販売系列の線の経路 | 受注→出庫→出庫明細という直列の経路 | 受注明細と出荷の2方向からの線が出庫1箇所に収束する経路 |
| 会員から伸びる線 | 受注への1本のみ | 受注と出荷への2本（会員が受注先と配送先の両方の起点になるため） |
| 中央付近の線の交錯 | 商品（マスタ）に全トランザクションの明細から参照線が集まる箇所でやや交錯 | 上記に加え、受注明細と出荷が出庫へ収束する箇所でも交錯が発生し、claude-only版より線が混み合う |
| 色分け | Mermaidのデフォルトテーマによる自動配色（分類上の意味はない） | テーブル分類（マスター＝緑／ステート＝黄／トランザクション＝赤）に対応させた意図的な配色 |

claude-only版は「受注1件に対して出庫がぶら下がる」シンプルな木構造のため、自動レイアウトでも
線の交錯は少ない。qiita-reference版は、受注明細と出荷という2つの独立した起点が出庫という1つの
テーブルに収束する構造（多対多の解消）を持つため、同じ自動レイアウトでも線が1箇所に集まり交錯が
増える。モデルが表現する業務の複雑さが、そのままER図の視覚的な複雑さとして表れる例になっている。

### 5.2 qiita-reference版内でのレイアウト手法の比較（Claude独自レイアウト vs 記事2のレイアウト原則）

同じqiita-referenceモデルに対して、2種類のER図を作成した。

- Claude独自レイアウト（全体図1枚）: [qiita-reference/er-diagram.png](qiita-reference/er-diagram.png)
- 記事2のレイアウト原則を適用した分割図（5枚）:
  [01](qiita-reference/er-diagram-layout-01-master-state.png) /
  [02](qiita-reference/er-diagram-layout-02-purchase.png) /
  [03](qiita-reference/er-diagram-layout-03-sales.png) /
  [04](qiita-reference/er-diagram-layout-04-stock-taking.png) /
  [05](qiita-reference/er-diagram-layout-05-tx-overview.png)

| 観点 | Claude独自レイアウト（全体図） | 記事2のレイアウト原則を適用した分割図 |
|---|---|---|
| 描画ツール | Mermaid（自動レイアウトエンジンに配置を一任） | Graphviz（rankを明示指定し、配置を手動で制御） |
| 図の数 | 1枚に14エンティティ全てを詰め込む | 系列ごとに4枚＋統合図1枚の計5枚に分割 |
| 線の形状 | 自動配置による曲線・斜め線が混在 | 直角にのみ曲がる線（斜め線なし）に統一 |
| 多重度の表記 | "1"／"N" の数字ラベル | 鳥の足記法（直角の短い線＝1、鳥の足記号＝多） |
| ページ比率 | 内容量に応じた可変サイズ | A4横（297:210）に統一。ボックスサイズは変えず余白で調整 |
| トランザクションの並び | 発生順の意識づけなし | 発生順に左から右へ配置 |
| 色分け | エンティティごとの自動配色 | マスター＝緑／ステート＝黄／トランザクション＝赤 |

最も大きな違いは、情報の一覧性と構造の読み取りやすさのトレードオフである。Claude独自レイアウトは
「1枚で俯瞰できる」が線が交錯しやすく、記事2の原則を適用した分割図は各系列の業務フローを直感的に
追えるが、全体の俯瞰には複数枚を行き来する必要がある。

### 5.3 qiita-reference版 vs rules-based版（同じレイアウトルールを異なる経路で適用した結果）

- qiita-reference版の統合図: [qiita-reference/er-diagram-layout-05-tx-overview.png](qiita-reference/er-diagram-layout-05-tx-overview.png)
- rules-based版の統合図: [rules-based/er-diagram-05-overview.png](rules-based/er-diagram-05-overview.png)

両者とも、CLAUDE.mdに記載したER図レイアウトルール（A4横比率、直角線、鳥の足記法、系列ごとの図分割、
マスタ・ステートの複製配置、テーブル分類別の色分け）を適用した結果である。qiita-reference版は
試行錯誤の過程（配色調整・レイアウト調整・文字重なりの解消等）を経て到達した図であるのに対し、
rules-based版はCLAUDE.md・requirements.mdのみを読んだ別経路での再現結果である。

| 観点 | qiita-reference版 | rules-based版 |
|---|---|---|
| 図の分割構成 | マスター・ステート／仕入れ系列／販売系列／棚卸し系列／統合図の5枚 | 同じ5枚構成（マスター・ステート／仕入れ／受注・出荷／棚卸し／統合図） |
| 用紙比率 | A4横に統一 | 同左（統合図は約1.414:1） |
| 線の形状 | 直角線のみ | 直角線のみ |
| 多重度表記 | 鳥の足記法 | 鳥の足記法 |
| 色分け | マスター＝緑／ステート＝黄／トランザクション＝赤 | 同じ3色の対応関係（彩度・塗りつぶし方はやや濃い目で、ヘッダー文字を白抜きにする等、具体的な配色の実装は独自） |
| マスタ・ステートの複製配置 | 商品・会員を参照元の近くに複製 | 同様に商品を5箇所、会員を2箇所に複製 |
| トランザクションに直接関連しないエンティティの省略 | カテゴリを統合図から省略 | 同様にカテゴリを省略 |
| 列情報の粒度 | 統合図はPKのみ、系列図はPK/FK＋業務属性 | 同様の使い分け |

図の構成・配置原則・色の対応関係・列情報の粒度の出し分けまで、独立した作業でほぼ同一の結論に
達している。差が出たのは、配色の具体的な実装（塗りの濃さやヘッダーの文字色）や、フォント・枠線の
太さといった美術的な細部のみであり、CLAUDE.mdに明記されていない部分である。これはER図レイアウトの
ルールについても、モデリングルールと同様に「構造的な原則は高い再現性を持つが、ビジュアルの微細な
調整はルール文書の記述密度に依存する」ことを裏付けている。

### 5.4 総括

- モデル構造の複雑さ（claude-only版 vs qiita-reference版）は、同じ自動レイアウトを使ってもER図の
  交錯具合に直接反映される。業務の実態を正確にモデル化するほど関連も増え、素朴なレイアウトでは
  読みにくくなるというトレードオフがある。
- そのレイアウト上の課題は、記事2の原則（分割・直角線・発生順配置・鳥の足記法・配色によるテーブル
  分類の明示）を適用することである程度解消できる。
- qiita-reference版とrules-based版の比較により、このレイアウト原則は個別の記事を直接参照しなくても、
  CLAUDE.mdというルール文書を介して独立に再現可能であることが確認できた。再現されなかったのは
  配色の具体的な実装など、ルールに明記されていないビジュアルの細部のみである。
- 結論として、複雑な業務ルールを正確に表現したモデルには、それに見合ったレイアウトの工夫を
  組み合わせて初めて実務で使える「読めるER図」になる。そして、その設計判断とレイアウトの工夫は、
  ルールとして言語化すれば（属性・命名・配色の細部を除き）高い再現性で引き継げることが、3版の
  比較から確認できた。
