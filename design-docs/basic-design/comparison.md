# データモデリング比較：Claude単独版 vs Qiita記事参考版

## 1. 比較の目的

本書は、以下の2つのモデリング結果を観点別に比較し、それぞれの長所・短所を整理した上で、
後続のER図作成の基礎とすべき設計を検討するための考察ドキュメントである。

- Claude単独モデリング版: [claude-only/data-model.md](claude-only/data-model.md)
- Qiita記事参考版: [qiita-reference/data-model.md](qiita-reference/data-model.md)

## 2. 観点別比較

### 2.1 テーブル分類の考え方

| | claude-only版 | qiita-reference版 |
|---|---|---|
| 分類の明示 | なし（マスタ／トランザクションという通俗的区別のみ暗黙的に使用） | 「マスターテーブル／ステートテーブル／トランザクションテーブル」を明示的に分類し、各テーブルをラベル付け |

qiita-reference版は、分類を明示することで「なぜこのテーブルにはステータス更新を許すのか／許さないのか」
という設計判断の根拠が追跡可能になっている。claude-only版はこの分類軸自体を持たないため、
各テーブルの可変性に関する方針が設計書上で説明されていない。

### 2.2 関連構築の優先順位

claude-only版は、一般的な業務システムの設計パターン（マスタ－トランザクション－明細）に沿って
関連を構築しており、特定の優先順位の原則は明文化していない。

qiita-reference版は、「トランザクション同士を業務プロセスの発生順に直接関連づけることを優先する」
という記事1の原則を明示的に採用している。結果として、仕入れ系列（仕入れ→入庫）・販売系列
（受注→出荷・出庫）のいずれも、トランザクションの連鎖として追跡可能な構造になっている。
この点は両版で大きな差はなく、claude-only版も結果的に同種の構造（仕入れ→入庫、販売→出庫）を
採用していたため、論理的な帰結は近い。

### 2.3 販売系列の構造（最大の差分）

| | claude-only版 | qiita-reference版 |
|---|---|---|
| 構造 | 販売（受注）1 : N 出庫 | 受注 1 : N 受注明細、受注明細 : 出荷 が 出庫（中間テーブル）を介して N : N |
| 分割出荷への対応 | 不可（1受注の出庫はすべて同一の出庫ヘッダに属する前提） | 可能（受注明細ごとに複数の出庫レコードを作成できる） |
| まとめ出荷への対応 | 不可（出荷は受注に従属する設計のため、複数受注を1回の出荷にまとめられない） | 可能（1つのshipmentに複数の受注由来のstock_outを集約できる） |

これが2版の最も本質的な差であり、記事3（受注と出荷は実際には多対多になる）の知見を反映したか
どうかによって生じている。claude-only版は一般的な「ヘッダ－明細」のパターンを素朴に適用した結果、
現実の配送業務で頻発する「複数注文の同時配送」「在庫切れによる分割配送」を表現できないモデルになった。

### 2.4 仕入れ系列の構造

両版とも「仕入れ 1 : N 入庫」というシンプルな構造で一致している。qiita-reference版では、
対称性のために仕入れ側も三層化（仕入れ→入荷→入庫）する選択肢を検討した上で、仕様に「入荷」に
相当する語が存在しないことを理由に見送った、という判断過程が明記されている点が差分である
（結果として生成される構造自体は claude-only版と同じ）。

### 2.5 ステータス管理

| | claude-only版 | qiita-reference版 |
|---|---|---|
| 進行状況の保持方法 | purchase_order / sales_order に `status` カラムを保持し、アプリケーション側で更新 | `status` カラムを廃止し、`is_cancelled` のみ保持。進行状況（未着手／一部実施／完了）は入庫・出庫レコードの集計から動的に導出 |

claude-only版は実装がシンプルだが、`status` と実際の入出庫実績が食い違う（更新漏れ等）リスクを
内在する。qiita-reference版は「トランザクションは追加後は基本的に更新されない」という記事1の原則に
忠実で、状態の単一の真実の源（Single Source of Truth）を入出庫の実績データに置いている分、整合性に
強いが、進行状況を求めるたびに集計クエリが必要になる。

### 2.6 在庫金額計算への言及

claude-only版は数量ベースの在庫算出のみに触れている。qiita-reference版は記事3の知見（先入先出法・
総平均法・移動平均法・最終仕入原価法による金額差異）を踏まえ、将来金額計算が必要になった場合の
留意点として明記している（仕様上は数量ベースの在庫算出のみが要求されているため、いずれの版も
金額計算ロジックの実装自体はスコープ外としている）。

## 3. 総括

| 観点 | 優れている版 | 理由 |
|---|---|---|
| 仕様文言との整合性 | qiita-reference版 | 仕様に明示される「出荷」と「出庫」を別概念として扱える |
| 実務的な表現力（分割・まとめ出荷） | qiita-reference版 | 出庫を中間テーブルとすることで多対多を自然に表現 |
| シンプルさ・学習コストの低さ | claude-only版 | テーブル数・関連数が少なく、素直な構造 |
| データ整合性の強さ | qiita-reference版 | ステータスの二重管理が発生しない |
| 実装・クエリの容易さ | claude-only版 | 進行状況をカラム参照のみで取得できる |

claude-only版は「標準的なECシステムのデータモデル」として素直で分かりやすいが、仕様文中に明示される
「出荷」という概念を独立したトランザクションとして扱っておらず、実務で頻発する分割出荷・まとめ出荷の
ケースに対応できない点が弱点である。

qiita-reference版は、著者自身が過去に実務で遭遇した課題（受注と出荷の多対多）を踏まえた設計になって
おり、仕様の文言（仕入れ・出荷・入庫・出庫をそれぞれ別概念として列挙している）とも整合的である。
一方で、販売系列が三層構造になることでテーブル数・関連数が増え、ステータスを集計で導出する設計は
実装時にクエリの複雑性を伴う。

## 4. 今後の方針（ER図作成の土台）

後続のER図作成ステップでは、**qiita-reference版をベースに採用する**。理由は以下の通り。

1. 仕様文中に「仕入れ」「出荷」「入庫」「出庫」という4つの語が明示的に列挙されており、
   出荷と出庫を別概念として扱うqiita-reference版の構造がこれに最も忠実である。
2. 分割出荷・まとめ出荷への対応力は、将来の要件変化に対する耐性として価値が高い。
3. ステータス導出による整合性強化は、販売管理システムとして妥当なトレードオフである。

ただし、qiita-reference版は販売系列が三層構造になっており、ER図上で可読性を保つ工夫が必要となる。
この点は記事2（ER図のレイアウト原則：トランザクションを発生順に横に並べる、親子関係は縦に並べる、
注目するモデルで図を分割する等）を適用して解決する方針とする。

## 5. ER図の比較

データモデルの比較に続けて、実際に作成したER図についても比較する。比較は2段階で行う。

- 5.1: claude-only版とqiita-reference版、それぞれのモデルをClaude単独の力でER図にした場合の違い
  （モデル構造の違いが図にどう表れるか）
- 5.2: qiita-reference版のモデルについて、Claude独自のレイアウトと、記事2の原則を適用したレイアウトの違い
  （同じモデルでも描き方でどれだけ可読性が変わるか）

### 5.1 claude-only版 ER図 vs qiita-reference版 ER図（モデル構造の違い）

比較対象は、どちらもMermaidの自動レイアウトエンジンに任せて1枚にまとめた全体図である。

- claude-only版: [claude-only/er-diagram.png](claude-only/er-diagram.png)
- qiita-reference版: [qiita-reference/er-diagram.png](qiita-reference/er-diagram.png)

| 観点 | claude-only版 | qiita-reference版 |
|---|---|---|
| 販売系列のエンティティ数 | SALES_ORDER, SALES_ORDER_DETAIL, STOCK_OUT, STOCK_OUT_DETAIL の4つ | SALES_ORDER, SALES_ORDER_DETAIL, SHIPMENT, STOCK_OUT の4つ（SHIPMENTが新規） |
| 販売系列の線の経路 | SALES_ORDER → STOCK_OUT → STOCK_OUT_DETAIL という直列の経路 | SALES_ORDER_DETAIL と SHIPMENT の2方向からの線が STOCK_OUT 1箇所に収束する経路 |
| MEMBERから伸びる線 | SALES_ORDER への1本のみ | SALES_ORDER と SHIPMENT への2本（会員が受注先と配送先の両方の起点になるため） |
| 中央付近の線の交錯 | PRODUCT（マスタ）に全トランザクションの明細から参照線が集まる箇所でやや交錯 | 上記に加え、SALES_ORDER_DETAILとSHIPMENTがSTOCK_OUTへ収束する箇所でも交錯が発生し、claude-only版より線が混み合う |
| 色分け | Mermaidのデフォルトテーマによる自動配色（エンティティごとにほぼランダムで、分類上の意味はない） | テーブル分類（マスター／ステート／トランザクション）に対応させた意図的な配色（5.2の配色方針を先取りして適用） |

claude-only版は「受注1件に対して出庫がぶら下がる」というシンプルな木構造になっているため、
自動レイアウトでも比較的素直に配置され、線の交錯は少ない。一方qiita-reference版は、受注明細と
出荷という2つの独立した起点がSTOCK_OUT（出庫）という1つのテーブルに収束する構造（多対多の解消）を
持つため、同じ自動レイアウトでも線が1箇所に集まり、交錯が増える。これは「モデルが表現する業務の
複雑さ（分割出荷・まとめ出荷）が、そのままER図の視覚的な複雑さとして表れる」例になっている。
言い換えると、qiita-reference版のモデルは表現力が高い分、素朴なレイアウトのままでは可読性が
犠牲になりやすく、5.2で述べるレイアウト上の工夫がより強く求められる。

### 5.2 qiita-reference版内でのレイアウト手法の比較（Claude独自レイアウト vs 記事2のレイアウト原則）

同じqiita-referenceモデルに対して、2種類のER図を作成した。

- Claude独自レイアウト（全体図1枚）: [qiita-reference/er-diagram.png](qiita-reference/er-diagram.png)
- 記事2のレイアウト原則を適用した分割図（4枚）:
  [01](qiita-reference/er-diagram-layout-01-master-state.png) /
  [02](qiita-reference/er-diagram-layout-02-purchase.png) /
  [03](qiita-reference/er-diagram-layout-03-sales.png) /
  [04](qiita-reference/er-diagram-layout-04-stock-taking.png)

| 観点 | Claude独自レイアウト（全体図） | 記事2のレイアウト原則を適用した分割図 |
|---|---|---|
| 描画ツール | Mermaid（自動レイアウトエンジンに配置を一任） | Graphviz（rankを明示指定し、配置を手動で制御） |
| 図の数 | 1枚に14エンティティ全てを詰め込む | 「マスター・ステート」「仕入れ系列」「販売系列」「棚卸し系列」の4枚に分割 |
| 線の形状 | 自動配置による曲線・斜め線が混在 | 直角にのみ曲がる線（斜め線なし）に統一 |
| 多重度の表記 | taillabel/headlabelによる"1"／"N"の数字ラベル | ER図の標準的な鳥の足記法（直角の短い線＝1、鳥の足記号＝多）による記号表現 |
| ページ比率 | 内容量に応じた可変サイズ | A4横（297:210）に統一。エンティティのボックスサイズは変えず余白で比率を調整 |
| トランザクションの並び | 発生順の意識づけなし（自動配置に依存） | 仕入れ→入庫、受注→出荷／出庫のように発生順に左から右へ配置 |
| ヘッダ・明細の配置 | 自動配置に依存し、縦に並ぶとは限らない | 同じrankに固定することで必ず縦に並ぶ |
| 色分け | エンティティごとの自動配色 | マスター＝緑、ステート＝黄、トランザクション＝赤の分類別配色 |
| 受注明細⇔出荷の多対多構造の見え方 | 線が交錯し、何と何が多対多の関係にあるのか読み取りにくい | 「分割して出庫されうる」「まとめて出庫されうる」の2本の矢印がSTOCK_OUTに収束する形で視覚的に明確 |

最も大きな違いは、情報の一覧性と構造の読み取りやすさのトレードオフである。Claude独自レイアウトの
全体図は「1枚で全体を俯瞰できる」利点があるが、エンティティ数が増えるほど線が交錯し、特に
qiita-reference版のように多対多を解消する中間テーブルを含むモデルでは、関連の意味を読み取るのが
難しくなる。記事2の原則（分割・直角線・発生順配置・鳥の足記法）を適用した分割図は、1枚あたりの
情報量を絞ることで、各トランザクション系列の業務フロー（発生順）と親子構造を直感的に追えるように
なっている一方、全体を俯瞰するには複数枚を行き来する必要があり、「ある商品がどのテーブルから
参照されているか」のような横断的な確認はしづらくなる。

### 5.3 総括

- モデル構造の複雑さ（claude-only版 vs qiita-reference版）は、同じ自動レイアウトを使っても
  ER図の交錯具合に直接反映される。業務の実態を正確にモデル化するほど、関連も増え、素朴な
  レイアウトでは読みにくくなるというトレードオフがある。
- そのレイアウト上の課題は、記事2の原則（分割・直角線・発生順配置・鳥の足記法・配色によるテーブル
  分類の明示）を適用することである程度解消できる。特に「出庫」のような中間テーブルを介した
  多対多構造は、トランザクションを発生順に横へ並べて中間テーブルに収束させる描き方と相性がよく、
  モデルの設計意図（記事3の知見）をそのままER図上の視覚的な構造として表現できた。
- 結論として、複雑な業務ルールを正確に表現したモデル（qiita-reference版）には、それに見合った
  レイアウトの工夫（記事2の原則）を組み合わせて初めて、実務で使える「読めるER図」になる。
  モデリングの精度とER図の可読性は別々の問題であり、どちらか一方だけでは設計書として不十分である。
